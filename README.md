# InsightX Backup

ปลั๊กอินย้าย/สำรองเว็บ WordPress ทั้งเว็บ (ฐานข้อมูล + ไฟล์) เป็นแพ็กเกจเดียว `.wpress` แล้วนำเข้ากลับ หรือส่งขึ้น S3-compatible storage ได้โดยตรง

> ⚠️ **หมายเหตุ:** ไฟล์ `.wpress` ของปลั๊กอินนี้เป็นฟอร์แมตของ InsightX เอง **ไม่ compatible** กับไฟล์ `.wpress` ของ All-in-One WP Migration แม้ใช้นามสกุลเดียวกัน — นำเข้าข้ามปลั๊กอินไม่ได้

---

## คุณสมบัติ

- **ส่งออก (Export)** — แพ็กฐานข้อมูล + ทั้ง `wp-content` (`plugins`/`themes`/`uploads`/`mu-plugins` และไฟล์/โฟลเดอร์อื่นๆ ที่อยู่ใต้ `wp-content` เช่น drop-in ไฟล์, `languages/`) เป็นไฟล์ `.wpress` เดียว ดาวน์โหลดเป็นไฟล์ หรือส่งขึ้น S3 โดยตรง
- **นำเข้า (Import)** — อัปโหลดไฟล์ `.wpress` (ลากวางหรือเลือกไฟล์) หรือนำเข้าจาก S3 โดยตรง ระบบกู้คืนไฟล์ + ฐานข้อมูล พร้อมแทนที่ URL/path/table-prefix ให้อัตโนมัติ แบบ **clean-then-restore** — ล้างไฟล์ `wp-content` เดิมก่อนกู้คืน และ drop ตารางเก่าที่ไม่อยู่ใน package หลังเสร็จ ผลลัพธ์ตรงกับ package เป๊ะ ไม่มีข้อมูลเก่าค้าง (ต่างจาก All-in-One WP Migration ที่เขียนทับอย่างเดียว)
- **ข้อมูลสำรอง (Backups)** — ทุกครั้งที่ export จะถูกเก็บสำเนาไว้ในเครื่องเสมอ ดูรายการ, กู้คืน, ดาวน์โหลด, ดูเนื้อหาไฟล์ข้างใน (พร้อมยอดรวมขนาดต่อโฟลเดอร์), หรือลบได้จากหน้าเดียว
- **การเชื่อมต่อ** — ตั้งค่า credential ของ Amazon S3, Minio, Garage, Cloudflare R2, DigitalOcean Spaces, Google Cloud Storage หรือปลายทาง S3-compatible อื่นๆ ได้พร้อมกันหลายเจ้า แยกการ์ดอิสระต่อ provider — ทดสอบเชื่อมต่อจริงทุกครั้งที่บันทึก ไม่ใช่แค่เช็คว่ากรอกครบ
- **ตั้งค่า Storage** — เลือกโฟลเดอร์เก็บ backup/job scratch ในเครื่องเอง (ค่าเริ่มต้นคือในปลั๊กอิน) และตั้ง **backup อัตโนมัติ** (รายวัน/รายสัปดาห์/รายเดือน ผ่าน WP-Cron, เลือกส่งขึ้น Storage ได้, จำกัดจำนวนไฟล์เก่าที่เก็บไว้)
- **Find & Replace** — แทนที่ข้อความในฐานข้อมูลตอน export ได้หลายคู่
- **ตัวเลือกขั้นสูง** — เข้ารหัสด้วยรหัสผ่าน, บีบอัด GZip (ต่อไฟล์ระหว่างแพ็ก ไม่ใช่ทั้งก้อนตอนจบ), ไม่รวมฐานข้อมูล/ตารางที่เลือก/คอมเมนต์สแปม/revision, ไม่รวมสื่อ/ธีม/ปลั๊กอิน (ทั้งหมดหรือเฉพาะที่ไม่ได้ใช้งาน)/ไฟล์แคช (เลือกเองเสมอ ไม่ exclude อัตโนมัติ)/ไฟล์ที่เลือกเอง
- **แสดงความคืบหน้าแบบละเอียด** — progress bar เดียวที่แสดงชื่อขั้นตอนปัจจุบัน (เช่น "เตรียมข้อมูล" → "ส่งออกฐานข้อมูล" → "แพ็กไฟล์" → "สร้างไฟล์สำเร็จ" → "อัปโหลดไปยัง Storage") พร้อม % เฉพาะขั้นนั้น (คำนวณจากจำนวนไฟล์/แถว/ไบต์จริง ไม่ใช่สูตรเดา — รวมขั้นอัปโหลดที่รายงานตามไบต์ที่ส่งขึ้น bucket ไปแล้วจริง) — พอขั้นไหนเต็ม 100% บาร์รีเซ็ตแล้วขึ้นขั้นถัดไปให้อัตโนมัติ มี shimmer animation วิ่งผ่านระหว่างทำงานให้เห็นว่าระบบยังทำงานอยู่แม้ % จะขยับช้า รวมช่วงอัปโหลดไฟล์ตอน import เป็นขั้นแรกด้วย พร้อมคำเตือนไม่ให้ปิด/ย้ายหน้าระหว่างทำงาน
  - บรรทัดข้อความใต้บาร์บอกรายละเอียดที่บาร์บอกไม่ได้ (เช่น `ส่งออกตาราง wp_posts (30000/100000 แถว)`, `กำลังรวบรวมปลั๊กอิน — 12345/15589 รายการ`) — ขั้นแพ็กไฟล์บอกด้วยว่ากำลังเก็บหมวดไหนอยู่ (ปลั๊กอิน → ธีม → คลังสื่อ → ไฟล์อื่นๆ ใต้ `wp-content`) ไม่ใช่แค่ตัวเลขรายการเฉยๆ — ขั้นอัปโหลดไม่มีบรรทัดนี้เพราะมีแต่ไบต์ซึ่งบาร์บอกไปแล้ว จะขึ้นเฉพาะตอนชิ้นไหนอัปโหลดขัดข้องแล้วกำลังลองใหม่
  - หน้าเว็บถามสถานะแบบปรับความถี่เอง — เริ่มที่ 300ms แล้วค่อยๆ ยืดถึง 2 วินาทีเมื่อค่าไม่เปลี่ยน แล้วกลับมาถี่ทันทีที่ขยับ ลดภาระเซิร์ฟเวอร์ระหว่างขั้นตอนที่กินเวลานาน
  - งานที่จบแบบล้มเหลว (เช่น อัปโหลดขึ้น Storage ไม่สำเร็จ) ขึ้นข้อความสีแดงแยกจากสำเร็จชัดเจน (ไม่ใช่กล่องข้อความปกติที่ดูเหมือนสำเร็จ) และซ่อนปุ่มดาวน์โหลดถ้า export ล้มเหลว
  - **ยกเลิกได้ทุกจังหวะ** — ปุ่ม "ยกเลิก" ใต้แถบความคืบหน้าหยุดงานได้จริงทุกขั้นตอน ไม่ใช่แค่ระหว่างที่ระบบว่าง งานหยุดภายในไม่กี่วินาทีแม้เว็บจะมีไฟล์เป็นแสนรายการ พร้อมปิด multipart upload ที่ค้างใน bucket ให้เรียบร้อย
- **หน้า Log แบบ real-time** — บรรทัด log ใหม่ขึ้นเองอัตโนมัติทุก 2 วินาทีระหว่างมีงานรันอยู่ (poll ผ่าน `isx_log_poll` เทียบ cursor ว่า log ยาวขึ้นกี่บรรทัดแล้วส่งมาต่อท้าย ไม่ reload หน้า) ไม่มีปุ่ม/checkbox รีเฟรชอีกต่อไป
- **รันต่อเนื่องแม้ปิดแท็บ** — งาน export/import ขับเคลื่อนด้วย WP-Cron เป็นตัวสำรอง นอกเหนือจากการ poll ของเบราว์เซอร์ — สลับหน้าหรือปิดแท็บระหว่างทำงานได้ งานจะยังเดินต่อในเบื้องหลัง (ต้องมีการเข้าเว็บ/ทราฟฟิกใดๆ เพื่อกระตุ้น WP-Cron ตามปกติของ WordPress) การ poll ยังทำงานต่อได้แม้ session หลุดกลางทาง (ดูหัวข้อความปลอดภัย)
- **ศูนย์รีเซ็ต (Reset Hub)** — เครื่องมือทำลายข้อมูลแบบถาวร 5 อย่าง: ล้างปลั๊กอิน (ยกเว้น InsightX Backup เอง) / รีเซ็ตธีมกลับเป็นค่าเริ่มต้น / ล้างคลังสื่อ / รีเซ็ตฐานข้อมูลทั้งหมด (สร้างผู้ดูแลใหม่ + login กลับเข้าอัตโนมัติ) / รีเซ็ตทั้งเว็บไซต์ (รวมทุกอย่างข้างต้น) — ทุกรายการต้องกรอกรหัสผ่านบัญชียืนยันก่อนทำ และมีปุ่ม "สร้างข้อมูลสำรองก่อน" ในตัวทุกการ์ด
- **WP-CLI** — `wp isx export` / `wp isx import <file>` / `wp isx providers` รันบนเซิร์ฟเวอร์ตรงๆ ไม่ต้องเปิดเบราว์เซอร์

## การติดตั้ง

### ดาวน์โหลด zip จาก GitHub

1. เข้า `https://github.com/InsightX-th/insightx-backup`
2. เมนูขวา **Releases** — เลือกเวอร์ชันล่าสุด แล้วดาวน์โหลดไฟล์ `insightx-backup-vX.X.X.zip` จากส่วน "Assets" (ไฟล์นี้ build จาก GitHub Actions แล้ว ไม่มี `.git`/`.github` ติดมา พร้อมอัปโหลดได้เลย)
   - ถ้า repo ยังไม่มี release เลย (ยังไม่เคย push tag) ให้ไปที่ **Tags** แทน แล้วกดดาวน์โหลด "Source code (zip)" ของ tag ที่ต้องการแทนได้ — ได้ผลเหมือนกัน
3. ไปที่เว็บ WordPress ปลายทาง → **Plugins → Add New → Upload Plugin**
4. เลือกไฟล์ zip ที่ดาวน์โหลดมา → กด **Install Now**
5. ถ้าเว็บนั้นเคยลงปลั๊กอินตัวนี้เวอร์ชันเก่ามาก่อน ให้ **Deactivate + Delete ตัวเก่าก่อน** แล้วค่อยอัปโหลดใหม่ (อย่าทับ) — กันปัญหา cache JS/CSS เก่าค้าง (ดูหัวข้อ "การอัปเดตปลั๊กอิน")
6. กด **Activate Plugin**

### ติดตั้งตรงจากโฟลเดอร์ (dev/local)

1. วางโฟลเดอร์ `insightx-backup` ไว้ที่ `wp-content/plugins/`
2. เปิดใช้งานปลั๊กอินจากเมนู **Plugins**
3. เมนู **InsightX Backup** จะปรากฏใน sidebar ของ wp-admin (มี 7 หน้าย่อย: ส่งออก / นำเข้า / ข้อมูลสำรอง / การเชื่อมต่อ / ตั้งค่า Storage / ศูนย์รีเซ็ต / Log)

**ความต้องการของระบบ:**

- PHP 7.4 ขึ้นไป
- ส่วนขยาย `cURL` (จำเป็นสำหรับ export/import ผ่าน S3)
- ส่วนขยาย `zlib` (จำเป็นสำหรับตัวเลือก "บีบอัด GZip")
- ส่วนขยาย `openssl` (จำเป็นสำหรับตัวเลือก "เข้ารหัสด้วยรหัสผ่าน" และเก็บ credential storage อย่างปลอดภัย)

## วิธีใช้งาน

### ส่งออกเว็บไซต์ (เมนู "ส่งออก")

1. **(ไม่บังคับ) Find & Replace** — กรอกคำที่ต้องการค้นหา/แทนที่ในฐานข้อมูล กด "+ เพิ่ม" เพื่อเพิ่มคู่คำอื่น
2. **(ไม่บังคับ) ตัวเลือกขั้นสูง** — คลิกเพื่อขยาย แล้วเลือกได้ตามต้องการ:
   - **ความปลอดภัย:** เข้ารหัสข้อมูลสำรองด้วยรหัสผ่าน (⚠️ ลืมรหัสผ่านแล้วกู้คืนไม่ได้ — เก็บไว้ให้ดี)
   - **การบีบอัด:** ไม่บีบอัด หรือ GZip (ไฟล์เล็กลง ใช้เวลานานขึ้นเล็กน้อย)
   - **ฐานข้อมูล:** ไม่รวมคอมเมนต์สแปม / ไม่รวม post revision / ไม่รวมฐานข้อมูลทั้งหมด / ไม่รวมตารางที่เลือกเอง (เปิด picker เลือกทีละตาราง) / ไม่ต้องแทนที่โดเมนอีเมล
   - **ไฟล์:** ไม่รวมคลังสื่อ / ไม่รวมธีม (ทั้งหมด หรือเฉพาะที่ไม่ได้ใช้งาน) / ไม่รวมปลั๊กอิน must-use / ไม่รวมปลั๊กอิน (ทั้งหมด หรือเฉพาะที่ไม่ได้เปิดใช้งาน) / ไม่รวมไฟล์แคช / ไม่รวมไฟล์ที่เลือกเอง (พิมพ์ path บรรทัดละ 1 รายการ เทียบกับ `wp-content/`)
3. **เลือกปลายทาง** — ถ้าจะส่งขึ้น Storage ให้เลือก provider จากการ์ด (ต้องตั้งค่าที่เมนู "การเชื่อมต่อ" ก่อน — provider ที่ยังไม่ตั้งค่าจะแสดงจางลง)
4. กด **"ส่งออกเป็นไฟล์"** เพื่อดาวน์โหลด หรือ **"ส่งออกไปยัง Storage"** เพื่ออัปขึ้น bucket โดยตรง
   - ไฟล์ที่ใหญ่กว่า 5MB จะอัปโหลดแบบ multipart อัตโนมัติ (แบ่งเป็นชิ้นละ 5MB — ปรับได้ผ่าน filter `isx_s3_part_size`, ระบบขยายขนาดชิ้นให้เองถ้าไฟล์ใหญ่จนจะทะลุเพดาน 10,000 ชิ้นของ S3) กันโดน reverse proxy หน้า bucket (เช่น Cloudflare) ตัดด้วย `413 Payload Too Large`
   - **อัปโหลดทำต่อจากจุดเดิมได้** — ส่งทีละชิ้นตามงบเวลาเท่ากับขั้นตอนอื่น (~10 วินาที/request) แล้วบันทึกตำแหน่งลง job state ทุกชิ้น ปิดแท็บ/worker ตายกลางทางแล้วงานเดินต่อจากชิ้นถัดไป ไม่เริ่มไฟล์ใหม่ทั้งก้อน แต่ละชิ้นลองใหม่ได้ 5 ครั้งก่อนยกเลิกทั้งงาน
   - ความคืบหน้าและเวลาที่เหลือคำนวณจากจำนวนไบต์ที่ส่งไปจริง (แถบเดินตามจริง ไม่ใช่ค้างที่ 100% รอจนจบ)
5. **เปลี่ยนใจกลางทางได้** — กด **"ยกเลิก"** ใต้แถบความคืบหน้า ยืนยันแล้วงานจะหยุดภายในไม่กี่วินาที ใช้ได้ทุกขั้นตอน (ส่งออกฐานข้อมูล, แพ็กไฟล์, อัปโหลดขึ้น Storage) ไม่ต้องรอให้ขั้นตอนปัจจุบันจบก่อน
   - งานที่ยกเลิกจะถูกปิดจริงทั้งฝั่งเซิร์ฟเวอร์ — ไฟล์ระหว่างทางถูกล้าง, ตัวขับงานเบื้องหลัง (loopback/WP-Cron) หยุดตาม, และ multipart upload ที่ค้างอยู่ใน bucket ถูกยกเลิกให้ ไม่มีอะไรเดินต่อเงียบๆ หลังปิดหน้า
   - ยกเลิก**ก่อน**ขั้น "สร้างไฟล์สำเร็จ" จะไม่ได้ไฟล์ `.wpress` เลย แต่ยกเลิก**ระหว่างอัปโหลดขึ้น Storage** ไฟล์จะอยู่ในเมนู "ข้อมูลสำรอง" เรียบร้อยแล้ว (ระบบเก็บสำเนาลงเครื่องให้ก่อนเริ่มอัปโหลดเสมอ) — ดาวน์โหลดหรือส่งขึ้น Storage ใหม่ทีหลังได้
6. ไฟล์ที่ export เสร็จจะถูกเก็บสำเนาไว้ในเมนู "ข้อมูลสำรอง" เสมอ ไม่ว่าจะเลือกปลายทางไหน — ตั้งชื่อไฟล์รูปแบบ `{โดเมนเว็บ}-{วันเดือนปี}-{รหัสสุ่ม 16 ตัว}.wpress` เช่น `skymaster.co.th-23072026-a1b2c3d4e5f6g7h8.wpress` (สุ่มยาว เพราะบนเซิร์ฟเวอร์ nginx ชื่อไฟล์คือสิ่งเดียวที่กันไม่ให้เข้าถึงไฟล์ backup ตรงจาก URL ได้ — ดูหัวข้อความปลอดภัย)
7. ลิงก์ดาวน์โหลด backup ชี้**ตรงไปที่ไฟล์เลย** (`storage/backups/...`) — เว็บเซิร์ฟเวอร์ส่งไฟล์เอง ไม่ผ่าน PHP อีกต่อไป จึงไม่มี PHP-FPM timeout / memory limit / proxy edge timeout มาตัดกลางทางได้ และได้ Range/resume มาฟรีจาก web server เอง (แนวทางเดียวกับที่ All-in-One WP Migration ใช้) — ใช้ได้เฉพาะตอนโฟลเดอร์เก็บ backup อยู่ใต้ web root เท่านั้น ถ้าตั้ง custom storage path ไว้นอก web root จะ fallback กลับไปสตรีมผ่าน `admin-ajax.php` แบบเดิม (ยังรองรับ Range เหมือนกัน แต่ผ่าน PHP)

### นำเข้าเว็บไซต์ (เมนู "นำเข้า")

⚠️ **การนำเข้าจะแทนที่เว็บปัจจุบันทั้งหมดด้วยเนื้อหาใน package (clean-then-restore) และต้องล็อกอินใหม่หลังเสร็จ** — ไฟล์ใน `wp-content` เดิม (คลังสื่อ, ธีม/ปลั๊กอินที่ไม่ได้เปิดใช้งาน, ไฟล์อื่นๆ ที่ไม่อยู่ใน package) จะถูกลบทิ้งก่อนกู้คืน และตาราง prefix เดียวกันที่ไม่อยู่ใน package จะถูก drop หลังนำเข้าเสร็จ — ยกเว้นปลั๊กอินนี้เอง + โฟลเดอร์ storage (ข้อมูลสำรองในเครื่อง) ที่ไม่ถูกแตะเสมอ การล้างไฟล์จะเริ่มก็ต่อเมื่อ package ผ่านการตรวจสอบแล้วเท่านั้น (ไฟล์เสียจะ error ก่อนโดยไม่แตะข้อมูลเดิม)

ธีม/ปลั๊กอิน/mu-plugins ที่**กำลังเปิดใช้งานอยู่** รวมถึง drop-in ไฟล์ (`object-cache.php`, `db.php` ฯลฯ) จะไม่ถูกลบทันทีในขั้นตอนล้างไฟล์ — เก็บไว้ให้เว็บยัง bootstrap ได้ตลอดช่วง import (เว็บต้องใช้ไฟล์พวกนี้ทุก request รวมถึง request ที่ poll ความคืบหน้าของ import เอง) แล้วค่อยลบส่วนที่ package ไม่ได้เขียนทับในขั้นตอนสุดท้ายหลังกู้คืนไฟล์+ฐานข้อมูลเสร็จสมบูรณ์แล้ว — ถ้า package export มาแบบไม่รวมปลั๊กอิน/ธีม (ตัวเลือก "ไม่รวมปลั๊กอิน"/"ไม่รวมธีม") ปลั๊กอิน/ธีมเดิมของเว็บปลายทางจะไม่ถูกแตะเลย

- **จากไฟล์ในเครื่อง** — ลากไฟล์ `.wpress` มาวางในกล่อง หรือกด "นำเข้าจาก" → "ไฟล์" เพื่อเลือกไฟล์
- **จาก Storage** — กด "นำเข้าจาก" → เลือก provider → ระบบโหลดรายการ backup ในนั้นอัตโนมัติ → กด "นำเข้า" ที่แถวไฟล์ที่ต้องการ
  - ถ้าไม่มีสิทธิ์ list bucket ให้ใช้ตัวเลือก "กรอกชื่อไฟล์เอง" (พิมพ์ object key เต็ม)
- ถ้าไฟล์เข้ารหัสด้วยรหัสผ่าน ระบบจะถามรหัสผ่านกลางกระบวนการนำเข้าอัตโนมัติ
- ไฟล์ที่บีบอัดด้วย GZip จะถูกคลายให้อัตโนมัติ ไม่ต้องทำอะไรเพิ่ม
- ตอนอัปโหลดไฟล์ในเครื่อง ถ้า chunk ไหนอัปโหลดไม่สำเร็จ (เน็ตสะดุด/เซิร์ฟเวอร์ error ชั่วคราว) ระบบจะลองใหม่อัตโนมัติสูงสุด 5 ครั้งก่อนค่อยแจ้งเตือนให้เริ่มใหม่

### ข้อมูลสำรอง (เมนู "ข้อมูลสำรอง")

- เมนู "ข้อมูลสำรอง" ใน sidebar ขึ้นตัวเลขจำนวนไฟล์สำรองที่มีอยู่เป็น badge (แบบเดียวกับ badge แจ้งเตือนอัปเดตของ WordPress) ไม่ขึ้นถ้ายังไม่มีไฟล์สำรองเลย
- กด **"สร้างข้อมูลสำรอง"** เพื่อ export แบบไฟล์อย่างเดียว (ไม่มี find&replace/ตัวเลือกขั้นสูง — export เต็มรูปแบบให้ไปที่เมนู "ส่งออก")
- แต่ละแถวมีปุ่ม **"..."** เปิดเมนู:
  - **กู้คืน** — นำเข้าไฟล์นี้กลับเข้าเว็บทันที (ไม่ต้องอัปโหลดใหม่)
  - **ดาวน์โหลด** (ลิงก์ตรงไปที่ไฟล์ ไม่ผ่าน PHP — ดูหัวข้อ "ส่งออกเว็บไซต์" ข้อ 6)
  - **ดูรายการ** — แสดงเนื้อหาข้างในแพ็กเกจเป็น folder tree (ขยาย/ยุบได้ทีละโฟลเดอร์) พร้อมขนาดไฟล์ โดยไม่ต้องแตกไฟล์ (ใช้ไม่ได้กับไฟล์ที่เข้ารหัส)
  - **ลบ** — ลบแถวออกทันทีไม่ต้องรีโหลดหน้า ถ้าเป็นแถวสุดท้ายจะขึ้นข้อความ "ยังไม่มีข้อมูลสำรอง" แทนตาราง

### การเชื่อมต่อ (เมนู "การเชื่อมต่อ")

ตั้งค่า credential ของแต่ละ provider แยกอิสระจากกัน (endpoint, region, bucket, access key, secret key, โฟลเดอร์ใน bucket, path-style URL) กด **"บันทึก"** ทีละ provider

- ทุกช่องจำเป็นต้องกรอก (ยกเว้น Endpoint URL ของ Amazon S3 ที่ล็อกไว้ เพราะคำนวณจาก Region อัตโนมัติ) — ปุ่ม **"บันทึก"** จะกดไม่ได้จนกว่าจะกรอกครบ
- ตอนกด "บันทึก" ระบบจะ**ทดสอบเชื่อมต่อจริง** (ListObjectsV2 ไปยัง endpoint/bucket ที่กรอก) ไม่ใช่แค่เช็คว่ากรอกครบ — ถ้า credential/bucket/endpoint ผิด จะขึ้น error จริงจากเซิร์ฟเวอร์ (เช่น HTTP 403/404/ชื่อ host resolve ไม่ได้) แทนที่จะขึ้น "เชื่อมต่อสำเร็จ" ทั้งที่ผิด
- **Path-style URL** — เปิดสำหรับ Minio/Garage/ปลายทาง self-hosted ส่วนใหญ่ ปิดสำหรับ AWS S3 (ใช้ virtual-hosted style)
- Secret Key ถูกเข้ารหัส AES-256-CBC ก่อนบันทึกลงฐานข้อมูลเสมอ ค่าที่แสดงเป็นจุด (`••••••••`) เป็นแค่ตัวยึดตำแหน่ง ไม่ใช่ค่าจริง — เว้นว่างไว้ตอนบันทึกซ้ำเพื่อคงค่าเดิม

**โฟลเดอร์ใน Bucket** — ตั้งชื่อโฟลเดอร์ที่จะเก็บ backup ได้เองต่อ provider ใส่ `/` คั่นเพื่อทำโฟลเดอร์ซ้อนได้ (เช่น `backups/production`) ปล่อยว่างไว้ = ใช้ `insightx-migrate` เหมือนเดิม (ค่าเริ่มต้นนี้คงชื่อไว้ตั้งใจ ไม่ตามชื่อปลั๊กอินที่เปลี่ยน — กัน backup เก่าที่อัปโหลดไปแล้วหายจากลิสต์) ชื่อที่กรอกถูกกรองให้เหลือเฉพาะ `A-Z a-z 0-9 . _ -` ต่อ segment และตัด `.`/`..` ทิ้ง ทั้งตอนบันทึกและตอนใช้งาน

การนำเข้าจาก Storage จะอ่านเฉพาะไฟล์ใต้โฟลเดอร์ของ provider นั้นเท่านั้น (เช็ค prefix ฝั่งเซิร์ฟเวอร์) — object key ที่ชี้ออกนอกโฟลเดอร์จะถูกปฏิเสธ

### ตั้งค่า Storage (เมนู "ตั้งค่า Storage")

**โฟลเดอร์เก็บ Backup ในเครื่อง** — พิมพ์ absolute path เอง (โฟลเดอร์แม่ต้องมีอยู่แล้วและเขียนได้) แล้วกด "บันทึก" ปล่อยว่างไว้ = ใช้ค่าเริ่มต้น (ในโฟลเดอร์ปลั๊กอินเอง) เปลี่ยน path ไม่ย้ายไฟล์เก่าให้อัตโนมัติ

**Backup อัตโนมัติ** — เปิดสวิตช์ เลือกความถี่ (รายวัน/รายสัปดาห์/รายเดือน) และปลายทาง (เก็บในเครื่องอย่างเดียว หรือ provider ที่ตั้งค่าไว้แล้วในเมนู "การเชื่อมต่อ") พร้อมจำนวน backup สูงสุดที่จะเก็บไว้ในเครื่อง (เกินแล้วลบตัวเก่าสุดทิ้งอัตโนมัติหลัง backup ใหม่สำเร็จ) — ขับด้วย WP-Cron เหมือน export/import ปกติ ต้องมีทราฟฟิกเข้าเว็บเพื่อกระตุ้นตามปกติของ WordPress

**การล้าง upload ที่ค้างใน bucket (อัตโนมัติ ไม่มีปุ่มให้กด)** — ไฟล์ที่ใหญ่กว่า 5MB อัปโหลดแบบ multipart (ดูหัวข้อ "ส่งออกเว็บไซต์" ข้อ 4) ถ้างานถูกยกเลิก เน็ตหลุด หรือ PHP worker ตายกลางทาง ชิ้นส่วนที่อัปไปแล้วจะ **ค้างอยู่ใน bucket โดยยังไม่กลายเป็นไฟล์จริง** — S3/R2 เรียกสถานะนี้ว่า "ongoing multipart upload" ซึ่งไม่โผล่ในรายการไฟล์ (`ListObjectsV2` มองไม่เห็น) ลบผ่าน object browser ของผู้ให้บริการไม่ได้ แต่ยังคิดค่าเก็บข้อมูลอยู่ ล้างได้ทางเดียวคือสั่ง `AbortMultipartUpload`

ปลั๊กอินจัดการให้เองทั้งหมด ไม่ต้องกดอะไร:

- **ยกเลิกทันทีทุกทางที่งานจบไม่สวย** — ส่งชิ้นไม่ผ่านครบ 5 ครั้ง, `CompleteMultipartUpload` ล้มเหลว, ตัวจับงานค้าง 5 นาทีตัดงานทิ้ง, กดปุ่ม "ยกเลิก" ระหว่าง export, หรือ job ถูกกวาดทิ้งหลังไม่มีสัญญาณชีพเกิน 1 ชั่วโมง
- **ทะเบียน upload ใน `wp_options`** (`isx_pending_uploads`) — upload ทุกตัวที่เว็บนี้เริ่มถูกจดไว้นอกโฟลเดอร์ job เพราะ job state หายได้ (เปลี่ยน storage path, ลบปลั๊กอิน, ดิสก์ถูกล้าง) พอ job ที่เป็นเจ้าของจบหรือหายไป ตัวที่ค้างจะถูกยกเลิก**ทันที** ไม่ต้องรอครบกำหนดเวลา — ทำงานตอนเริ่ม export ครั้งถัดไปและตอนเปิดหน้า wp-admin
- **ของที่ไม่มีเจ้าของ** (ค้างมาจากเวอร์ชันก่อนมีทะเบียน หรือมาจากเว็บอื่นที่ใช้โฟลเดอร์เดียวกัน) — วันละครั้ง ปลั๊กอินจะ `ListMultipartUploads` ใต้โฟลเดอร์ของตัวเองแล้วยกเลิกตัวที่เก่าเกิน 12 ชั่วโมง ต้องมีเกณฑ์อายุเพราะ upload ที่**กำลังอัปอยู่จริง**ก็อยู่ในสถานะ pending เหมือนกัน ยกเลิกทันทีจะไปฆ่า export ของเว็บอื่นที่ยังทำงานอยู่ (ปรับเวลาได้ด้วย filter `isx_foreign_upload_max_age`)
- สั่งเก็บกวาดเดี๋ยวนี้เองได้ด้วย `wp isx cleanup-uploads` (มี `--dry-run` ให้ดูก่อน)

### ศูนย์รีเซ็ต (เมนู "ศูนย์รีเซ็ต")

⚠️ **ทุกเครื่องมือในหน้านี้ทำลายข้อมูลอย่างถาวรและย้อนกลับไม่ได้** — ต้องมีสิทธิ์ `manage_options` เท่านั้นถึงจะเห็นเมนูนี้ (เข้มกว่าเมนูอื่นที่ใช้ `export`/`import`)

- **ล้างปลั๊กอิน** — ปิดใช้งาน + ลบปลั๊กอินอื่นทั้งหมดออกจากเว็บ ยกเว้น InsightX Backup เอง
- **รีเซ็ตธีม** — สลับไปใช้ธีมเริ่มต้นของ WordPress ก่อน แล้วลบธีมอื่นทั้งหมด
- **ล้างคลังสื่อ** — ลบไฟล์สื่อ + attachment post ทั้งหมดในคลังสื่อ
- **รีเซ็ตฐานข้อมูล** — ลบทุกตารางในฐานข้อมูล (ตาม prefix ของเว็บนั้น) แล้วสร้าง schema ใหม่ตามค่าเริ่มต้นของ WordPress, สร้างบัญชีผู้ดูแลใหม่ (login เดิม + รหัสผ่านสุ่มใหม่) และ login ให้อัตโนมัติก่อน request จบ (ไม่ต้อง re-login เอง) — ค่าตั้งค่าของ InsightX Backup เอง (path ที่เก็บ backup, ตารางเวลา backup อัตโนมัติ, credential S3) ถูกสำรองไว้ก่อนแล้วใส่กลับหลังรีเซ็ต ไม่หายไปด้วย
- **รีเซ็ตทั้งเว็บไซต์** — รันทั้ง 4 อย่างข้างต้นเรียงกัน (ปลั๊กอิน → ธีม → คลังสื่อ → ฐานข้อมูล เป็นลำดับสุดท้ายเสมอ)

ทุกปุ่มต้อง**กรอกรหัสผ่านบัญชีปัจจุบันยืนยันก่อนเสมอ** (เช็คฝั่งเซิร์ฟเวอร์ด้วย `wp_check_password()` ไม่ใช่แค่ popup ฝั่งเบราว์เซอร์) และมีปุ่ม **"สร้างข้อมูลสำรองก่อน"** อยู่คู่กันทุกการ์ด (เรียก export flow ปกติ) — แนะนำให้กดสร้างข้อมูลสำรองก่อนใช้เครื่องมือใดๆ ในหน้านี้เสมอ ด้านล่างสุดของหน้ายังมีลิสต์ข้อมูลสำรองทั้งหมดให้ดู/กู้คืน/ดาวน์โหลดได้เหมือนเมนู "ข้อมูลสำรอง"

## WP-CLI

```bash
# ส่งออก ดาวน์โหลดไว้ในเครื่อง (storage/backups/)
wp isx export

# ส่งออกแล้วอัปขึ้น Storage provider ที่ตั้งค่าไว้แล้ว (ดู slug จาก wp isx providers)
wp isx export --to=amazon_s3

# นำเข้าไฟล์ .wpress ที่อยู่บนเซิร์ฟเวอร์แล้ว (ยืนยันก่อนเขียนทับเว็บ ข้ามด้วย --yes)
wp isx import /path/to/backup.wpress
wp isx import /path/to/backup.wpress --yes

# ดู slug ของ provider ที่ตั้งค่า/เชื่อมต่อสำเร็จแล้ว
wp isx providers
```

## การอัปเดตปลั๊กอิน

เช็คเวอร์ชันใหม่อัตโนมัติจาก GitHub (`github.com/InsightX-th/insightx-backup`) ผ่าน [plugin-update-checker](https://github.com/YahnisElsts/plugin-update-checker) (vendored ไว้ใน `libs/`) — ขึ้น "There is a new version available... update now" ในหน้า Plugins แบบเดียวกับปลั๊กอินที่อัปเดตผ่าน WordPress.org

**วิธี release เวอร์ชันใหม่:**

1. อัปเดตเลขเวอร์ชันให้ตรงกันทั้ง 3 จุด: `Version:` ใน header ของ `insightx-backup.php`, `ISX_VERSION` ในไฟล์เดียวกัน และ `Stable tag:` ใน `readme.txt` (พร้อมเพิ่ม changelog entry ใน `readme.txt`)
   - ⚠️ **เลขเวอร์ชันห้ามถอยหลัง** — update checker เทียบเลขของ release ล่าสุดกับที่ติดตั้งอยู่ ถ้าปล่อยเลขต่ำกว่าที่เว็บปลายทางมีอยู่ เว็บนั้นจะไม่เห็นอัปเดตอีกเลยจนกว่าจะไปอัปเดตมือ
   - ไฟล์ JS/CSS **ไม่ต้องพึ่งการ bump เวอร์ชัน**เพื่อล้างแคชเบราว์เซอร์อีกแล้ว — `ISX_Admin::asset_ver()` เอา `filemtime` ของไฟล์ต่อท้าย `ISX_VERSION` ใน query string ของทุก asset (เช่น `?ver=0.1.8.1753939200`) แก้ไฟล์เมื่อไหร่เบราว์เซอร์โหลดใหม่เมื่อนั้น เดิมทีลืม bump แล้วเว็บที่อัปเดตมาจะได้ HTML ใหม่แต่ยังรัน JS เก่า (เคยทำให้ปุ่ม "ยกเลิก" ขึ้นมาแต่กดไม่ติด และช่อง "โฟลเดอร์ใน Bucket" กดบันทึกแล้วค่าหาย)
2. Commit + push แล้ว `git tag -a v0.1.x -m "InsightX Backup v0.1.x" && git push github v0.1.x`
   - ⚠️ tag ต้องชี้คอมมิตที่ push ขึ้น remote แล้วเท่านั้น — ถ้า tag ค้างอยู่แต่ในเครื่อง เว็บปลายทางจะไม่เห็นอัปเดตเลย เพราะ update checker อ่านจาก GitHub Release ไม่ใช่จาก working tree
3. `.github/workflows/release.yml` จะรันอัตโนมัติตอน push tag — build zip ด้วย `git archive` (จาก tracked tree ของ tag นั้น, ไม่มี `.git`/ไฟล์ dev-only ติดไปเพราะ `.gitattributes` สั่ง `export-ignore`) แล้วสร้าง GitHub Release แนบ zip เป็น release asset
4. เว็บที่ลงปลั๊กอินไว้จะเห็นอัปเดตใหม่ภายในรอบเช็คถัดไป (หรือกด "Check again" ในหน้า Plugins)

Repo เป็น public ไม่ต้องตั้งค่า access token ฝั่ง WordPress — ถ้าเปลี่ยนเป็น private ทีหลัง ต้องเพิ่ม token ให้ `PucFactory::buildUpdateChecker()` ใน `insightx-backup.php`

## ความปลอดภัย

- โฟลเดอร์ `storage/` ระดับบนสุด (job scratch data ระหว่าง export/import + logs) ถูกกัน HTTP access โดยตรงด้วย `.htaccess` (`Require all denied`, รองรับทั้ง Apache 2.4 และ 2.2 ผ่าน `<IfModule>`) + `index.php` ว่างเปล่า
- **`storage/backups/` (ไฟล์ `.wpress` ที่เก็บถาวร) ตั้งใจ _ไม่_ deny-all** — อนุญาตให้เข้าถึงไฟล์ `.wpress` ได้ตรงๆ (แค่ปิด directory listing) เพื่อให้ปุ่มดาวน์โหลดชี้ตรงไปที่ไฟล์แล้วให้เว็บเซิร์ฟเวอร์ส่งเองได้เลย ไม่ผ่าน PHP — แนวทางเดียวกับ All-in-One WP Migration ผลคือ **ดาวน์โหลดไม่มีการเช็ค nonce/capability ใดๆ อีกต่อไป** ความปลอดภัยพึ่งชื่อไฟล์สุ่ม 16 ตัวอักษรล้วนๆ (`ISX_Backups::store()`) ถ้าใครเดา/หลุด URL ไฟล์ได้ก็โหลดได้แม้ไม่ได้ login — บนเซิร์ฟเวอร์ nginx (ที่ไม่อ่าน `.htaccess` เลย) ชื่อไฟล์สุ่มนี้คือชั้นป้องกันจริงชั้นเดียว
- ตั้ง custom storage path ไว้**นอก web root** จะไม่มี URL ตรงให้ใช้ (`ISX_Backups::is_web_reachable()` เป็น false) ระบบจะ fallback กลับไปดาวน์โหลดผ่าน `admin-ajax.php` แบบสตรีมผ่าน PHP อัตโนมัติ — เส้นทางนี้ยังเช็ค nonce/capability ตามปกติ
- ตั้ง custom storage path แล้วเซิร์ฟเวอร์ใช้โฟลเดอร์นั้นไม่ได้ (ไม่มีอยู่จริง/เขียนไม่ได้) จะไม่ลบค่าที่ตั้งไว้ทิ้งเงียบๆ — ระบบ fallback ไปใช้โฟลเดอร์เริ่มต้นชั่วคราวพร้อมขึ้น admin notice เตือนในหน้า wp-admin แทน กันปัญหางานที่กำลังรันอยู่หายไปกลางทางเพราะ path เปลี่ยนโดยไม่รู้ตัว
- แต่ละ export/import job มี secret แยกต่อ job เก็บบนดิสก์ ใช้ยืนยันตัวตนแทน WP session ระหว่าง poll (เพราะ import เขียนทับ `wp_users`/`wp_options` กลางทาง ทำให้ session เดิมหลุด) — endpoint poll (`isx_run`) ลงทะเบียนทั้งแบบ `wp_ajax_` และ `wp_ajax_nopriv_` เพื่อให้ยัง poll ต่อได้แม้ WP มองว่า "ไม่ login" แล้ว โดยที่ยังปลอดภัยเพราะเช็ค secret เท่านั้น ไม่เช็ค capability ใดๆ ที่ endpoint นี้
- ตาราง `{prefix}options` ถูก import แบบ **atomic เสมอ** (ไม่ตัดข้ามหลาย AJAX request แม้จะมีแถวเกินขีดจำกัดปกติของตารางอื่น — ดู `ISX_Import::database()`) เพราะ WordPress ทุก request ต้องอ่านตารางนี้ก่อนถึงจะ bootstrap ได้ (รู้ว่าปลั๊กอินไหน active) ถ้าตัดข้าม request จะเสี่ยงเจอสถานะ options ไม่ครบระหว่างทาง ทำให้ปลั๊กอินไม่ถูกโหลดและ import ค้างถาวรกู้เองไม่ได้ — มี safety net เสริมใน `finalize()` เติม plugin ตัวเองกลับเข้า `active_plugins` ถ้าหายไปจริงๆ
- ปิด WP Heartbeat API ทุกหน้าของปลั๊กอินระหว่าง export/import/กู้คืน กัน modal "session expired" ของ WP core มาแทรกกลาง progress UI
- Secret Key ของ S3 destinations เข้ารหัสด้วยกุญแจที่มาจาก `wp_salt('auth')` ของเว็บนั้นๆ ก่อนเก็บลง `wp_options`
- ไฟล์กลางทาง (archive/DB dump/file list) ของ job ถูกลบทิ้งทันทีเมื่อ export/import เสร็จสมบูรณ์ — เหลือแค่ state ชิ้นเล็กๆ ไว้ประมาณ 5 นาทีกันงานชนกัน (browser poll กับ WP-Cron driver) แล้วค่อยถูกกวาดทิ้งตอนมีการสร้าง job ถัดไป
- เมนู "ศูนย์รีเซ็ต" ต้องมีสิทธิ์ `manage_options` เท่านั้น (เข้มกว่าเมนูอื่นที่ใช้ `export`/`import`) และทุก action ต้องผ่านการยืนยันรหัสผ่านบัญชีฝั่งเซิร์ฟเวอร์ก่อนเสมอ ไม่ใช่แค่ capability + nonce เหมือนเมนูอื่น — กันการกดพลาด/กด AJAX ตรงๆ โดยไม่ได้ตั้งใจ

## การแก้ปัญหา — HTTP error code ตอนเชื่อมต่อ/อัปโหลดไป Storage

ข้อความ "เซิร์ฟเวอร์ตอบกลับ HTTP xxx: ..." ที่ขึ้นตอนกด "บันทึก" (หน้าการเชื่อมต่อ) หรือ "ส่งออกไปยัง Storage" คือ status code ที่ตอบกลับมาจาก **endpoint ของ provider ที่กรอกไว้จริงๆ** (`ISX_S3_Client`, `includes/class-isx-s3-client.php:215-217`) ไม่ใช่ error จากปลั๊กอินเอง — โค้ดแค่ส่งต่อ status + message ที่ endpoint ตอบมาให้เห็นตรงๆ ตารางนี้ช่วยไล่สาเหตุตาม code:

| Code                                                | ความหมาย                                                                                                                                                               | สาเหตุที่พบบ่อยกับ S3-compatible storage                                                                                                                                                                                                                                                                                                 |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **400** Bad Request                                 | Request ผิดรูปแบบ                                                                                                                                                      | Region/endpoint ไม่ตรงกับที่ bucket ตั้งไว้จริง, path-style เปิด/ปิดผิดฝั่ง (ดูหัวข้อ "Path-style URL" ด้านบน)                                                                                                                                                                                                                           |
| **401** Unauthorized                                | ยืนยันตัวตนไม่ผ่าน                                                                                                                                                     | Access Key / Secret Key ผิด หรือ signature คำนวณผิด (เวลาเซิร์ฟเวอร์เพี้ยน — SigV4 ผูกกับเวลาปัจจุบัน)                                                                                                                                                                                                                                   |
| **403** Forbidden                                   | ยืนยันตัวตนผ่านแต่ไม่มีสิทธิ์                                                                                                                                          | Key ถูกแต่ไม่มี permission เขียนเข้า bucket นี้, bucket policy บล็อกไว้                                                                                                                                                                                                                                                                  |
| **404** Not Found                                   | หา resource ไม่เจอ                                                                                                                                                     | ชื่อ bucket พิมพ์ผิด/ไม่มีอยู่จริง, endpoint URL ผิด                                                                                                                                                                                                                                                                                     |
| **405** Method Not Allowed                          | endpoint ไม่รับ HTTP method นี้                                                                                                                                        | มักเจอตอน endpoint ที่กรอกไม่ใช่ S3 API จริงๆ (เช่น กรอก URL หน้าเว็บ/console แทน API endpoint)                                                                                                                                                                                                                                          |
| **429** Too Many Requests                           | โดน rate-limit                                                                                                                                                         | ยิง request ถี่เกินที่ provider กำหนด (พบยากกับปลั๊กอินนี้เพราะ retry มี backoff อยู่แล้ว)                                                                                                                                                                                                                                               |
| **500** Internal Server Error                       | ปัญหาฝั่ง provider เอง                                                                                                                                                 | บั๊ก/ปัญหาชั่วคราวที่ต้นทาง ไม่เกี่ยวกับ config ฝั่งเรา                                                                                                                                                                                                                                                                                  |
| **502** Bad Gateway / **503** Service Unavailable   | Proxy หน้า provider เข้าไม่ถึง backend จริง หรือ backend ล่ม/overload ชั่วคราว                                                                                         | provider กำลังบำรุงรักษา/ล่มชั่วคราว รอแล้วลองใหม่                                                                                                                                                                                                                                                                                       |
| **504** Gateway Timeout                             | Proxy รอ backend นานเกินจนตัดการเชื่อมต่อ                                                                                                                              | ไฟล์ใหญ่/เน็ตช้า ทำให้ request เดียวไม่จบใน time budget ของ proxy                                                                                                                                                                                                                                                                        |
| **520–527** (Cloudflare-specific)                   | Cloudflare (ถ้า endpoint อยู่หลัง Cloudflare) เจอปัญหาคุยกับ origin server ไม่ได้ตามที่คาด                                                                             | origin ตอบกลับแปลกๆ/reset การเชื่อมต่อกลางทาง — ปัญหาฝั่ง origin/network ระหว่าง Cloudflare กับ origin ไม่ใช่ credential                                                                                                                                                                                                                 |
| **521** Web Server Is Down                          | origin server ปิดพอร์ตที่ Cloudflare คุยด้วย                                                                                                                           | เซิร์ฟเวอร์ปลายทางไม่ได้เปิดรับการเชื่อมต่อจริง                                                                                                                                                                                                                                                                                          |
| **522** Connection Timed Out                        | Cloudflare ต่อไปยัง origin ไม่ติดภายในเวลาที่กำหนด                                                                                                                     | Firewall/network ปลายทางบล็อก หรือ origin ตอบช้าเกิน                                                                                                                                                                                                                                                                                     |
| **523** Origin Is Unreachable                       | Cloudflare หา route ไปยัง origin ไม่เจอ                                                                                                                                | DNS/routing ของ origin มีปัญหา                                                                                                                                                                                                                                                                                                           |
| **524** A Timeout Occurred                          | ต่อ origin ติดแต่ origin ไม่ตอบกลับทันเวลา (มักเจอกับไฟล์ใหญ่ที่ประมวลผลนาน)                                                                                           | อัปโหลดไฟล์ใหญ่จน origin ใช้เวลาตอบนานกว่า Cloudflare ยอมรอ                                                                                                                                                                                                                                                                              |
| **525/526** SSL Handshake / Invalid SSL Certificate | คุย TLS กับ origin ไม่สำเร็จ                                                                                                                                           | Certificate ที่ origin หมดอายุ/ไม่ตรงโดเมน                                                                                                                                                                                                                                                                                               |
| **530** พร้อม `error code: 1033`                    | **Cloudflare Tunnel (Argo Tunnel) ไม่ได้เชื่อมต่ออยู่** — endpoint ที่กรอกไว้ชี้ผ่าน Cloudflare Tunnel แต่ tunnel ฝั่ง origin ไม่ได้รันอยู่/ขาดการเชื่อมต่อตอนนั้นพอดี | ปัญหาอยู่ฝั่ง origin server ทั้งหมด ไม่เกี่ยวกับ Access Key/Secret Key ที่กรอกในปลั๊กอิน — ต้องไปเช็คว่า `cloudflared`/tunnel service ที่ origin รันอยู่จริงไหม (ดู `cloudflared tunnel info`/log ของ tunnel), หรือถ้าเป็น service ที่เช่าใช้ (เช่น MinIO ผ่าน Cloudflare Tunnel) ต้องเช็คกับผู้ดูแล service นั้นว่า tunnel ล่มหรือเปล่า |
| **530** อื่นๆ (ไม่มี 1033)                          | DNS resolve endpoint ไม่ได้ทั่วไป (Cloudflare 1016 error family)                                                                                                       | พิมพ์ endpoint ผิด/โดเมนไม่มีอยู่จริง/DNS record ของโดเมนนั้นถูกลบ                                                                                                                                                                                                                                                                       |
| Transport error (ไม่มี HTTP status เลย, status = 0) | คุยกับ endpoint ไม่ได้ตั้งแต่ระดับ connection (`ISX_S3_Client` บรรทัด 208-212)                                                                                         | DNS resolve ไม่ได้/timeout ที่ระดับ cURL เอง/ไม่มี extension cURL ในเซิร์ฟเวอร์ (ข้อความจะขึ้น `ต้องมีส่วนขยาย PHP cURL...` แทน)                                                                                                                                                                                                         |

**หลักการไล่:** โค้ด `4xx` (400/401/403/404) ต้องไปแก้ที่หน้า "การเชื่อมต่อ" — credential/endpoint/bucket ผิด ไปเช็คตรงนั้นก่อน ส่วนโค้ด `5xx` และ Cloudflare `52x/530` เป็นปัญหาฝั่ง provider/origin ที่ปลั๊กอินแก้เองไม่ได้ ต้องรอ provider หาย หรือติดต่อผู้ดูแล origin นั้น
